Property Portal

A property marketplace for buying, selling, and renting real estate, launching in Yangon and Mandalay with a location model ready for future expansion.

Review status: This is a product and technical specification only. It intentionally contains no implementation.

1. Purpose

Build a web-first property marketplace for Myanmar. The first release supports Yangon and Mandalay, their townships, and neighborhoods. A mobile application follows after the web experience and API are stable.

2. Product goals

  • Help visitors discover properties by transaction type, location, category, price, and features.
  • Let owners and agents publish and manage listings.
  • Let buyers and renters save, compare, and enquire about properties.
  • Provide moderation and operations tools for admins and staff.
  • Share a TypeScript API/domain contract across web and mobile.
  • Launch with substantial realistic sample data for Yangon and Mandalay.

3. Initial scope

Transaction types

BuySellRent

Seller-side workflows use “Sell”; public seller listings are discoverable under the Buy marketplace.

Property categories

LandApartment / condominiumHouseCondo unitCommercialOfficeShop / retailWarehouseIndustrialRoom / shared accommodationOther

Categories are data-driven. Category-specific attributes must be extensible without changing the core listing model.

Locations

Use a hierarchical location model: city → township → optional ward/neighborhood. Listings reference a location ID. Seed Yangon and Mandalay first; future cities must not require schema redesign.

4. Users and permissions

RoleCapabilities
VisitorBrowse, search, filter, view public details, and submit enquiries.
Buyer / renterVisitor actions plus profile, saved listings, saved searches, enquiry history, and viewing requests.
OwnerCreate/manage own listings, upload media, receive/respond to enquiries, and view performance.
AgentManage assigned/owned listings, agency profile, enquiries, and optional owner collaboration.
StaffModeration and operational workflows within assigned permissions.
AdminFull administration, roles, taxonomy, locations, audit access, and staff permissions.

Roles are additive. A user may have multiple roles. All access checks are enforced server-side.

5. Core user journeys

  1. Search for an apartment for rent in Yangon, refine results, inspect a listing, and contact the owner/agent.
  2. Save and compare listings.
  3. Create a listing as draft, add photos/location, submit for review, and publish after approval.
  4. Manage multiple agent listings and respond to enquiries.
  5. Review, change-request, or reject submitted listings with a moderation reason.
  6. Add future locations, update categories, manage staff permissions, and audit admin changes.

6. Functional requirements

Discovery

  • Responsive list/grid search with map-ready location data.
  • Filters for transaction, category, city, township, prices, bedrooms, bathrooms, areas, furnishing, parking, amenities, status, and date posted.
  • Sort by relevance, newest, price, and area.
  • URL-addressable search state, pagination/cursors, and clear loading/error/empty states.
  • Listing details include gallery, price, location, attributes, description, amenities, contact CTA, owner/agent, verification, related listings, and report action.

Listing management

Lifecycle: draft → submitted → changes_requested / approved_published → paused / sold_rented / archived. Support category-dependent required fields, ordered media, cover image, captions, public slugs, verification, and private moderation history.

Engagement and administration

  • Saved listings, saved searches, enquiries, viewing requests, notification records, and abuse reports.
  • Moderation queue, users, roles, agencies, categories, amenities, locations, audits, and dashboard metrics.

7. Technical architecture

The projects are three sibling repositories:

property-portal/
  api/      # Express API, Prisma, SQLite
  app/      # React web application, shadcn/ui
  mobile/   # React Native + Expo application (later phase)

Each repository owns its package/configuration/tests/README/Git history. Shared types are published or generated as a versioned package or API contract.

API

TypeScript, Node.js, Express, Prisma 7, and SQLite initially. REST JSON under /api/v1. Use validation, policies, services, repositories, structured logs, request IDs, rate limits, secure CORS, OpenAPI, access/refresh-token auth, and replaceable media storage.

Web

TypeScript + React with shadcn/ui preset b7CNFsdU. Provide accessible responsive UI, typed API client, server-state caching, route authorization, and Myanmar-aware MMK/metric formatting with Burmese/English-ready content.

Mobile

React Native + Expo + TypeScript. Consume the same API; prioritize discovery, listing details, saves, enquiries, notifications, and listing management.

8. Logical data model

User, Role, Permission, UserRole, Profile, Agency, AgencyMember, Location, PropertyCategory, Amenity, Listing, ListingAmenity, ListingAttribute, ListingMedia, SavedListing, SavedSearch, Enquiry, ViewingRequest, ModerationReview, Report, AuditLog, and Notification.

Listings include title, slug, description, transaction/category, status, owner/agent, location, price/currency, negotiability, bedrooms, bathrooms, areas/units, furnishing, parking, contact visibility, publication timestamps, and verification metadata. Use decimal-safe money/area storage, indexes, opaque IDs, timestamps, archive/soft-delete semantics, and avoid SQLite-only assumptions that block PostgreSQL migration.

9. Initial API surface

  • Auth: /auth/register, /auth/login, /auth/refresh, /auth/logout, /me
  • Listings: list/create/detail/update/submit/pause endpoints
  • Engagement: save/unsave, saved searches, enquiries, viewing requests
  • Reference data: locations, categories, amenities
  • Dashboards: owner/agent listings and enquiries
  • Administration: moderation, users, taxonomy, locations, reports, audits

Pagination, filtering, sorting, validation, authentication, and authorization errors must have one documented response format.

10. Sample data and seed requirements

  • Development-only accounts for every role.
  • At least 100 realistic listings across Yangon/Mandalay, major categories, and buy/rent transactions.
  • Varied prices, areas, rooms, amenities, statuses, owners, agents, agencies, media placeholders, saves, enquiries, and moderation records.
  • Township/neighborhood hierarchy that exercises filters and sorting.
  • Repeatable, idempotent seed script with no real personal data, credentials, or production secrets.

11. Quality, security, and accessibility

  • Strict TypeScript, lint/format checks, and CI.
  • Unit tests for domain/policies; API integration tests for auth, lifecycle, filters, and role boundaries; web E2E tests for primary journeys.
  • WCAG 2.1 AA-oriented keyboard access, labels, focus, contrast, and non-color status cues.
  • Input validation/sanitization, auth/contact rate limiting, safe upload MIME/size limits, IDOR protection, and secret management.
  • Reproducible migrations/seeds, health checks, error/latency/auth/moderation monitoring, and backups.

13. Definition of done for web MVP

  • Visitors can find and inspect buy/rent listings in Yangon and Mandalay.
  • Role-based actions and records are correctly isolated.
  • Owners/agents can submit listings through moderation to publication.
  • Buyers/renters can save listings and send enquiries.
  • Staff can moderate with recorded reasons; admins can manage locations/categories.
  • Seed data covers filters, roles, statuses, and workflows.
  • Automated checks pass and primary journeys work at desktop and narrow viewport sizes.
